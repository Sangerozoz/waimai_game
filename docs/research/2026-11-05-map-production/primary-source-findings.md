# 县城地图生产管线：一手来源核查

日期：2026-11-05。范围：外部官方资料与生产案例研究，不是工程实测，不修改代码、素材或导航。已阅读 `docs/product/implementation-baseline.md` 当前地图条目；本文件是技术建议，不能自动覆盖用户认可的25图、原道路、三层边界和既定测试授权。

## 结论

**下一步最值得验证的是“原路网驱动的确定性地面与道路＋独立建筑对象”，而不是再要求AI整图锁住全部道路。** 这里的确定性是指道路、河道、建筑落点与骑手都从同一世界坐标生成；2D建筑还是3D建筑是第二个独立选择。Cocos有实现这些选择的能力，官方文档没有证明本团队已经具备达到认可画风的资产生产能力。

建议保留原导航图及业务ID，把道路与河道从生成式图片中拿出来，独立制作；建筑、植物、庭院按完整对象管理。固定镜头允许采用2D精灵，但**这不是一条未经尝试的新方法**：项目旧单件拼装已有美观、单一地面、无种植区、门朝向、骑手比例、无阴影六项失败；3D几何样板也未达到美术要求。下一步应验证的是“合格资产来源＋完整场景制作＋可重复导出”，不是再次证明sprite或模型能显示。如果只能获得彼此透视不一致的单体AI图，继续拼装也会重复失败；可比较由有经验的美术制作/授权购买适配的3D模块，再选择运行时3D或离线渲染成2D精灵。**不把程序盒子加窗、未经修整的AI单楼图或“模型能加载”算作美术路线成功。** 这是根据下述资料和项目失败条件作出的工程推断，并非引擎官方的项目推荐。

## 官方能力核查及实际含义

| 已核实事实 | 对本项目的含义与限制 |
|---|---|
| Cocos 3.8提供静态/动态Mesh创建，交给MeshRenderer显示。[程序创建网格](https://docs.cocos.com/creator/3.8/manual/en/asset/model/scripting-mesh.html) | 原路中心线可生成有宽度的道路网格。路口求并、弯道接头、桥梁、UV与路沿仍需实现，API不会自动完成道路设计。 |
| 相机提供正交投影、视口与裁剪参数，Layer/Visibility也作用于Sprite。[相机](https://docs.cocos.com/creator/3.8/manual/en/editor/components/camera-component.html) | 可以固定真实投影，而非让每次生成图片自己理解镜头。正交投影不会自动使不一致的素材变一致。 |
| Canvas下可用Sorting2D或节点顺序；非Canvas 2D可通过自定义材质启用深度测试。[渲染顺序](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/engine/priority.html) | 建筑与骑手的遮挡必须显式设计。节点顺序、世界高度与地面坐标不是同一概念；没有“拖进引擎自动按楼体排序”的依据。具体Sorting2D可用性需核实项目补丁版本。 |
| 2D合批要求材质、纹理、缓冲与状态等一致；Graphics不参加通常的2D合批，TiledMap有独立内部合批。[2D合批规则](https://docs.cocos.com/creator/3.8/manual/en/ui-system/components/engine/ui-batch.html) | 不宜先默认几千段Graphics道路或大量独立PNG必然高效；可离线合成地面小块，或按区生成Mesh。遮挡顺序可能打断合批，不能为了少DrawCall把骑手压到所有建筑上。 |
| 3D实例合批适合同网格/材质；同批透明物体不排序，静态合批也有变换等限制。[MeshRenderer](https://docs.cocos.com/creator/3.8/manual/en/engine/renderable/model-component.html) | 重复模块有性能工具，但“开实例化即可处理所有树叶和透明楼体”不成立。透明、阴影、材质数量仍要预算。 |
| Asset Bundle支持按需加载/预载/释放；removeBundle不会释放已加载资源。[资源包](https://docs.cocos.com/creator/3.8/manual/en/asset/bundle.html) | 可以组织分区资源；开发方仍要实现可视范围、预加载、缓存与卸载生命周期。导航图不必随美术区块卸载。 |
| 3.8提供屏幕占比驱动的LODGroup和模型简化；普通2D/UI不直接受它管理。[LOD](https://docs.cocos.com/creator/3.8/manual/en/editor/rendering/lod.html) | 3D可做远近模型切换；2D远景简化须另做缩略块或对象筛选。固定正交镜头下，不能仅按相机距离套透视场景的LOD经验。 |
| FBX/glTF可导入，并提供网格优化、简化。[模型导入](https://docs.cocos.com/creator/3.8/manual/en/asset/model/mesh.html) | 有可靠DCC至引擎入口；材质、比例、支点、风格仍是资产交付规范，不能从支持格式推出可自动产出资产。 |

## Tiled能解决什么

Tiled的对象层可任意放置对象，支持点、多边形、折线和自定义属性；等距图对象坐标存在特殊投影约定，需要转换。[对象层与坐标](https://doc.mapeditor.org/en/stable/manual/layers/) 因而它可以作为人工审阅/调整地块、建筑落点、遮挡切片、交互锚点的编辑器，不需要把既有任意角度路网硬改成菱形格。

`.world`用位置关联多张地图，并提供仅看相邻地图的编辑选项；无限地图允许画布扩展。[World](https://doc.mapeditor.org/en/stable/manual/worlds/)、[无限地图](https://doc.mapeditor.org/en/latest/manual/using-infinite-maps/) **这是编辑格式与编辑器行为，不是Cocos自动运行时流式加载的证明。** Cocos文档列出TMX/TSX/图片导入及其版本关系，3.8.5还改变过瓦片边缘处理。[Cocos Tiled资源](https://docs.cocos.com/creator/3.8/manual/en/asset/tiledmap.html) 若选Tiled，应先验证实际项目版本对有限TMX、对象层/属性、图集边缘和所需导出格式的支持；未确认前不把.world/无限TMX作为生产依赖。

建议：既有世界坐标JSON继续是权威；需要人工编辑时转换为Tiled对象层并保存sourceId，导出时做一次统一坐标转换。不要令Tiled像素坐标、道路米制坐标、图片锚点三套数据分别手调。

## 三条路线的生产比较（以下为研究判断）

| 路线 | 可以稳定控制的部分 | 最难的真实工作 | 当前建议 |
|---|---|---|---|
| 原路矢量/Mesh＋分块地面＋独立2D楼/树精灵 | 路宽、路口、道路连续性、落点、区块归属；可保留原图ID与导航 | 素材统一镜头/光照/清晰度、完整足迹、复杂遮挡拆片、地块设计、批次与显存 | 有条件采用；旧拼装已失败，只有合格资产与完整场景的新增证据才值得再验证，不能靠扩数量证明成功 |
| 原路Mesh＋真实3D模块＋固定正交镜头 | 真几何、相机、比例、深度、方向和光照统一；道路与建筑共享世界 | 建模/材质/UV、艺术指导、模块多样性、场景布置、阴影与平台性能 | 有合格资产来源时可信；程序挤出楼不等于该路线美术交付；无法承诺独立开发者快速产出整县 |
| 以AI整图为权威，反建导航 | 有机会让角色沿某张图里可见的道路走 | 遮挡段如何连通、路河分辨、路口拓扑、相邻图不一致、POI重定位、旧ID/距离/业务迁移，仍无高清补偿 | **不推荐当前项目使用**。已有可靠原路网，改追错误图片会引入第二次地图重建；导航也不能治好视觉断路/切楼 |

第三条不是理论上永远做不了：如果允许重新设计路网，并由人工制图把一张最终画面整理成无歧义的权威底图，可以描路、建图、核验可达性。但本项目明确保留原道路与经营范围，25图也不是一张几何自洽地图，故缺少该路线成立的前提。未发现本次查阅的一手资料支持“任意AI城市插画可以自动可靠反建生产级配送导航”的承诺。

## 成熟游戏案例给出的警示

Factorio官方记录：旧铁路图块通过翻转旋转省资源，但限制透视；改用更立体的画法后，交叉关系出现问题，需要增加/拆分图层。[FFF163：铁路与遮挡](https://www.factorio.com/blog/post/fff-163) 这支持“复杂对象需预先提供层次信息”的判断，不能证明所有建筑仅按一个Y值就能正确遮挡。

该团队又记录，角色/车辆通常逐方向渲染以保持照明；更大的多变体动画会迅速推高帧数。[FFF411：逐方向渲染成本](https://www.factorio.com/blog/post/fff-411) 因而固定相机能降低需求；把同一张斜俯视楼图任意旋转90度不会产生新的正确立面与光照。离线3D渲染精灵是一条可控资产路线，但需要先有模型和统一渲染设置。

其高分精灵造成显存压力，atlas能够减少提交开销，也可能增加显存分配困难；树图的大块空白同样浪费资源。[FFF227：纹理与显存](https://direct.factorio.com/blog/post/fff-227) 此为该游戏2018年的经验，不能把其显存数值当本项目预算或性能证书。

官方还说明，平面格与视觉斜俯视不一致会让特效和游戏效果的对应产生额外补偿。[FFF357：投影代价](https://www.factorio.com/blog/post/fff-357) 本项目已有原路世界坐标，更应先确定统一投影，而不是复制某款游戏有意采用的特殊视觉折衷。

## 建议的可重复生产过程

以下为项目方案建议，不是已经实现的状态：

当前固定高俯角约60～65°、方位约45°、退距6～10m，少量穿帮可接受；不需要自由旋转、拆建或动态灯光（本地项目要求，经父任务核实）。因此不应把实时全3D当作硬需求。可烘焙统一阴影和静态材质，减少运行时负担；但门口朝向、树的种植区、庭院地面和人物尺度必须在实际场景中审阅。

1. **冻结唯一世界定义。** 保存道路/河道/三框/sourceId哈希，明确米制轴、原点、相机方位、俯角、投影矩阵、缩放上下限。地面、车轮接地点、楼足迹、POI统一由它投影。62.5°/45°之类既有机位参数应从工程和底稿核对，不从一张AI图反猜。
2. **确定性生成地面。** 用原中心线与宽度生成道路面，独立处理交叉口、桥、沿岸和路沿。生成可覆盖全县的简单正确地面是工程工作；地面质感和周围场地仍需美术。
3. **地块与对象归属。** 每栋完整建筑有唯一owner、世界足迹、接地锚点、视觉包围盒与遮挡信息。跨区只改变索引/加载引用，不裁半楼、不生成两份不同版本。道路按全局几何切块，边缘共用同一数据；分块不是分开重新设计。
4. **资产验收后再布置。** 先覆盖低层住宅、多层住宅、办公、公共设施、树等必要形态。每件明确实际原生像素、每米像素、镜头、阴影、alpha、足迹、入口和可否旋转。AI图只可作为候选、材质或概念来源；需要人工修整才能成为合格对象时，应把工时计入。
5. **定义遮挡策略。** 地面永远在下；常规独立对象可按接地基准排序；大足迹/凹形/桥梁/门廊需拆前后片或显式遮挡关系。不能用一个全县固定层让骑手总在最上/最下。选择3D时用真实深度并专门处理透明材质；使用2D深度材质也仍需正确的几何/深度信息。
6. **再做资源分块与预算。** 加载可视区及必要邻圈，依据视觉包围盒防止高楼在足点出屏后提前消失；卸载渲染资产时保持导航/订单逻辑连续。地面可烘焙成高分小块，建筑保留独立对象；无需强迫所有内容使用瓦片。

### 与上次失败相比，必须补出的证据

应要求一个**完整地块场景包**：不只一栋裸楼，还包括对应的铺地/院落边界、入口方向、台阶/道路接入、树池/花坛、适配树种、地面阴影、少量设施及与骑手同框的比例。每个内容都按原路约束布置，但允许以整体场景Prefab/组合包复用，而不是复制所有街区同一摆法。程序可以负责组合与坐标；审美和资产设计要有可信来源。

如果选3D至2D离线管线，需保存可重开的源模型、统一相机/灯光配置和批量导出脚本，证明改一处能重导出而不漂移；如果选绘制/AI修整的2D管线，需保存源层、像素尺度、遮挡片、阴影层和可复用落点规范，证明第二张能匹配第一张。若选择购买素材包，要先核对许可、源文件、统一风格/镜头及功能类型覆盖，再决定补作量。以上是新增证据要求，不是本轮已有资产。

验收比较应逐项对照旧六项失败：同屏美观、地面材质/边界丰富、树有种植设计、门口朝路且可接入、骑手大小与楼体比例明确、统一日间地面阴影。只提供一张没有骑手或没有入口的美图，不能证明旧问题已解决。

## 分辨率约束：先算预算再挑生产粒度

以下是算术估计，不是对已存25图的配准测量。若3.3km横向由5个1254像素区组成，忽略halo、斜向投影和浪费，横向最多约6270有效样本，即约1.9像素/米。在35m横向近景中约67源像素；若该方向占1080屏幕像素，需要约16倍放大。实际参数需按投影和区块有效核宽重算，但这一量级已足以说明：**换成25张、合为大图、改PNG或加载进Cocos都不会增加近景细节。**

通用预算应按最紧视角计算：地面纹理密度至少接近该方向的 `屏幕像素 / 可见世界长度`，再检查斜向与建筑高度；2D楼图依据它最大显示像素准备。小尺寸可重复纹理、向量边线、独立高分楼体能把细节预算分配到近景对象。3D几何可保持轮廓，但低分材质和粗糙模型仍会暴露，不能等同无限清晰。

仅作RGBA8解码基底算例：25×1254²×4约150MiB；完整mip链再约增加1/3，未计副本、图集空白、缓冲与平台格式。磁盘PNG压缩大小不等于这部分内存。实际应按构建纹理格式和真机采集，而不以此估计宣布通过或失败。

## 扩全县前的验证门槛

这些是后续决策用门槛，本轮不执行游戏测试，也不声称用户已经授权新路线实施。

- **代表性小区块要能重复生产**：约100～200m可作为初始范围建议，选至少两个原道路路口、弯道、河/桥、两类建筑及跨分块完整楼体。不能只选没有交叉/遮挡的漂亮街角。
- **几何先过**：路线中心、可见路面、骑手轮接地点来自同一坐标。人工走查各路口与桥段，无车骑进楼、河或图中断路；原图导航拓扑/ID不被改写。具体视觉容差沿用用户允许小地砖误差，不能把明显占路降格成小误差。
- **遮挡先过**：角色经过楼前/后、树后、拐角和跨区点时无整楼翻层/突然消失；公开列出无法用单张sprite解决的对象。
- **近景先过**：按既定最小视宽和目标设备像素检查，列出纹理原生尺寸与屏幕显示尺寸；用户看到的必须是工程实机画面，不是高分概念图替代。
- **生产先过**：用同套规范再交第二个不同地块，记录生成、人工修整、定位、接入的时间和返工原因。第一块偶然好看不足以支持整县承诺。没有专业资产修整能力时，如实承认成本/来源缺口。
- **性能需后续获准后实测**：密集视口、缩放/横移、连续跨块；记录设备、构建、帧时分布、DrawCall、内存峰值、加载卡顿及卸载后回落。若产品目标60fps，其帧预算约16.7ms，30fps约33.3ms；目标由产品/平台决定，官方功能列表不提供本项目合格证明。

人力判断：这至少包含工程（投影/路网地面/分块/排序）、环境美术（楼型/材质/场地）、技术美术（资产规格/导出/atlas/遮挡）和审阅职责，可以由少数人兼任，但不能省略职责。当前工具可写代码、编辑JSON、做候选图，不代表已具备持续制作统一风格的专业模型/精灵库。没有资产能力证据时，不承诺全县天数、画风达标率或“最后一次方法必定成功”。
