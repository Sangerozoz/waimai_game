## 项目经理的决策与沟通

- 用户只需向项目经理给目标、优先级、反馈或验收结果。项目经理负责把这些信息转成专业任务，并在本会话统一汇报，不要求用户去各角色之间搬运消息。
- 可自主决定：已获准目标内的实现方法、日常技术与制作细节、分批大小、任务顺序、返修和回归安排、模型/强度及成本控制。
- 需汇总给用户决定：产品定位、玩法或阶段范围的重大变化，无法从现有要求推断的重要体验取舍，以及需要额外授权的实际发布或不可逆操作。先准备具体可审阅结果，避免泛泛提问。
- 专业角色在本角色会话完成报告，并把证据保存到项目文件；项目经理用会话状态工具与报告收集进度。无需给项目经理额外发反向消息来重复报告。需用户选择的缺口写入报告，由项目经理统一处理。

## 派工与交接

每次派工包含：任务编号、目标、引用的已确认来源、执行范围/文件归属、前置依赖、明确交付物、验收条件、允许的验证方式和当前停止点。

状态使用：待排期 → 已派工 → 执行中 → 待复核 → 待用户体验验收（仅确有需要时）→ 完成。阻塞另记原因、证据和可继续的独立工作。消息已发、文件已存在、构建通过和体验验收通过分别记，不能相互替代。

游戏策划先列需求与验收 → 项目经理安排优先级和依赖 → 美术/音效/动画按任务交付资源与规格 → 开发集成并自检 → 测试独立核对 → 项目经理汇总证据与需用户体验的项目。运营按对应阶段提供目标玩家、内容与发行需求。无资源依赖的任务可并行；改同一文件的工作顺序安排。

美术继续沿用 `docs/art/2026-10-29-production-workflow.md` 及需求清单：策划 → 美术（提示词/分批）→ GPT 普通聊天。角色母版先于同人头像与阶段变体，已有图标、车辆、餐品、底板不重复生图。

## 模型分配原则

- 文件清点、状态登记、格式整理、已有模板下的常规提示词：轻量模型、低或中等强度。
- 常规功能实现、完整任务拆解、跨文件需求核对：能力足够的工作模型、中等强度；复杂度增高时提升。
- 复杂玩法/架构设计、棘手回归、存档/经济安全、高风险独立审查：强模型和适当的高强度。
- 模型随具体任务调整，不给某角色永久绑定最强模型；不为简单接单空转强推理，也不把关键任务交给无法胜任的模型。记录实际派工设置，不将“建议使用”写成“已经生效”。
