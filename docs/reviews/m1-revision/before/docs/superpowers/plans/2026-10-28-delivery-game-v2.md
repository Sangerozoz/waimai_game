# 《送外卖》V2七阶段实施方案

> 后续获得实施指令后，使用executing-plans按已开放阶段任务执行，复核与验收点以本文为准。本轮只交付方案，不运行这些实施任务。

**目标：** 在保留当前进度和已完成工作的基础上，分阶段交付有参与感、可规划、有持续正收益及恢复路径的配送经营游戏。

**状态：本轮仅规划，未开工。** 规则依据[新版整体设计](../specs/2026-10-28-delivery-game-v2-design.md)。新参数是首轮试算，需阶段验收后调整。原T01–T12为历史任务映射，不与本版M1–M7混算完成状态。

**架构：** 统一操作入口下区分订单、骑手行程、地点动作和资源；真实寻路复用，预计与执行同源；逐单钱/经验/评价和实际行驶里程独立登记；新存档版本与旧活动兼容隔离。

**技术：** 现有Cocos Creator 3.8.8、TypeScript、Web Mobile、纯逻辑检查及持久化检查。用户负责页面与手感验收，助手检查代码/数值/兼容/构建；没有新授权不自动操作页面。

## 二、全阶段不得破坏的约束

- 钱、经验、评价、路线、已确定结果和历史回执不因迁移丢失；新规则只作用于对应版本，旧活动先按旧规则完成。
- 不点加速也能正常经营；点击倍率有限，同一行程时限和位移一起推进，在线/NPC/日切不加速。
- 订单先取后送、最多3单、实际携带不超载；M2仍限1单。追加与重排先校验后提交，不消耗旧计划。
- 重复触摸、重试、刷新、后台/尺寸变化不重复发钱、扣钱、恢复体力或抽结果。
- 超时仍能交付，无强制现金罚款；免费恢复不依赖余额/广告/尚未解锁地点。
- 账单按真实本地日期与实际业务统计，新口径不拿旧账单未知历史倒推。
- 不在未完成阶段展示假功能；未上线灰色无事件，未解锁收益隐藏，不添加底栏状态小字。
- 每阶段有完整恢复点、源码/规则标识、验收记录和已知限制；P1/P2阻断缺陷处理后才推进依赖它的下一阶段。

范围：保留现有单单模式，不把V2新规则塞进当前验收。

- [ ] 用户重点复验点位内缩/城区分布、首次点击响应、2秒取餐提示、需求弹窗、60%黑蒙层、最新导航与账单。
- [ ] 对用户发现的问题定向修复；代码/数值/存档/类型/构建验证，保存错误可见。
- [ ] 修正现行餐品固定轮换导致易碎5/16=31.25%、与县城目标10%不符的生成偏差；先确定普通/耐放余下权重，再按类别选餐品。已有候选和已接结果保留，以足量生成流校验目标频率，不用完成单选择分布代替；当前只记录问题、尚未改代码。
- [ ] 记录当前规则基线与恢复快照，保留真实存档，不代填用户验收。

出口：原存档能连续送、攒钱买D+、重开不丢钱/重复发奖；用户接受现有操作。当前168项检查是历史技术证据，不能当作V2或真机已通过。目标手机首屏≤3秒、低端≥30fps仍需实际设备证据。

## 四、M2：单单行程、到点操作与点击加速

这是近期最细实施包，包含必要底层变更，交付仍为只接一单的完整可玩版本。

### M2.1 统一状态、时间与迁移

预期新增文件位于`delivery-game/assets/scripts/map-sample/`：`DeliverySessionV2.ts`、`TripClock.ts`、`GameplayProfile.ts`、`DeliverySnapshotV4.ts`。职责分别为统一状态操作、时钟积分/停靠边界、版本化参数、新快照校验/旧活动兼容。名字为计划接口，不宣称当前已存在。

消费者只知道少量操作与只读状态；状态变更结果包含事件和待提交快照：

```ts
type DeliveryAction =
  | {type:'depart'} | {type:'accelerate';inputTimeMs:number}
  | {type:'confirmPickup';stopId:string}
  | {type:'confirmDelivery';orderId:string;answers:Record<string,boolean>}
  | {type:'advance';foregroundMs:number};
// 每个提交附commandId和expectedRevision；只读状态含jobs、trip、player、events。
```

- [ ] 先写并运行缺口检查：服务2秒/60游戏秒独立、同路径快慢点结果一致、大dt停在人工边界、零距离段、重复确认、后台不推进。
- [ ] 用单调revision/动作状态防重，持久化种子与事件键保证重启后同一随机结果；待提交期间冻结后续经济/移动边界命令。
- [ ] 验证Web宿主跨页单写者锁或事务存储；同revision并发仅一方可提交，另一方只读重载。不能以localStorage比较后写代替原子提交。
- [ ] 建立V4校验，明确移除旧“所有活动单等于同一playerBefore钱包”等单单约束；允许0单有行驶里程，补给支出字段先保留为0。
- [ ] 以旧版本1/2/3的idle/routes/running/arrived/done夹具做迁移。旧活动不加新体力、不改时钟/餐损；旧done仅展示，不重复入账或补账。
- [ ] 旧活动完成前不开新NPC计息与新资产变更；行程冻结收入相关参数，禁止有活动单时切换玩家车/城市、改站点或队伍配车，不能只靠UI置灰约束。
- [ ] 保存失败、有效备份、损坏主档、未知未来版本和旧标签冲突都有明确结果；迁移前留原始快照。

### M2.2 加速与地点操作

涉及现有`MapSample.ts`、`OrderPhone.ts`、`CityMap.ts`、`SampleUI.ts`；UI只发操作，不自行加钱或扣资源。

- [ ] 新行驶基础换算与有界点击倍率接入同一行程时钟，旧活动继续旧适配路径。
- [ ] 只在moving显示加速；点击叠加、停止衰减，停靠和后台清零。不把地图拖动当加速，不影响真实在线时长。
- [ ] 到商家点取餐后完成2秒动作，到顾客点送达或处理需求；服务中重载只继续剩余动作。
- [ ] 加入辨认所需的按压、车速/行驶动效、取送反馈与基础声音，素材来源明确；无实际声音时记录未交付项，不能称音效已完成。
- [ ] 使用不点、慢点、密集点、低帧率与不同窗口的实际逻辑检查，保持按钮首次响应和地图边界。

### M2.3 账单与集成交付

- [ ] V2按实际行驶增量记里程，跨真实午夜先切段，允许当日0完成但有路程；在线仍真实前台时间。
- [ ] 旧兼容活动不同时登记V2行驶增量，只按旧完成口径记一次原路线；旧单结束后才切新里程口径，防迁移时双计。
- [ ] 保留12项账单及旧历史下限，逐单结算的唯一登记不受UI重开影响。
- [ ] 定向检查→完整回归→类型→Cocos构建→独立复核→用户页面体验，记录真实未测项。

出口：用户能从当前位置自动去取餐并送达；20游戏分钟道路段不点10秒，均匀8次/秒点击的候选数学值约3.33秒，M2实测误差与手感需记录，取餐2秒另算，不承诺整单3秒。不点也能完成；同计划点击强度不改游戏到达时刻、费用、风险或里程；旧单、途中/服务中重载不出错。点击是否有趣、是否像机械点按，由用户体验决定，未接受前先调整，不急着叠三单。

## 五、M3：三单规划

预期新增`TripPlanner.ts`（合法取送顺序、真实路段、载重、ETA）、扩展会话/快照/大厅/规划面板。体力功能仍关闭。

- [ ] 开放1–3单，接取前证明至少存在一条物理合法计划；候选与持有单分开，重复订单ID拒绝。
- [ ] 10个稳定订单槽位在出发前只保留/撤回，不补新ID、不推进随机游标；反复接3单再撤回仍是原大厅，不能绕过每日刷新额度。仅首次真实交付与合法手动刷新补候选。
- [ ] 最多6个必要任务，枚举先取后送的顺序；同店合并、同店超载需分次回访、单行路、不可达路径、零距离相邻点都覆盖。
- [ ] 预览新增绕行、每单ETA/迟到、逐段携带重量；迟到是可选取舍，不通过重置时限把它消除。
- [ ] 停靠点允许重排剩余任务；行驶中不瞬移改起点，暂不开途中接单。非法重排保持原计划可继续。
- [ ] 每单结算更新当前钱包/评价/经验；同趟收入参数冻结、升级不回写已出发余单；三单回执、货物和里程互不串用。
- [ ] 构建同店同方向、反方向高价单、2单各3kg但需先送再取、1单已送另2单未取、同帧跨两站等固定案例，并生成大量合法/非法顺序验证。

出口：存在可观察的顺路优势和绕路代价；接3单不是强制；三单分别完成、超时和结算正确，旧单/多单途中及交付后恢复不丢进度，实际共同路程只计一次。若策略差异只停留在文字而无实际结果，不进入M4。

## 六、M4：体力、补给与净收益

预期新增`RiderResources.ts`（消耗/恢复/上限）、`SupplyRules.ts`（价格/耗时/一次性支付）、扩展规划、快照、账单及补给弹窗。使用[首轮候选参数](../../reviews/gameplay-v2/trial-profile.json)，随验证版本化调整，不在UI硬编码。

- [ ] 按真实距离保留消耗残差，低帧率和密集点击不增加耗能；同店合并按服务次数扣。
- [ ] 完整预演每段到达补给前的体力、补给后的封顶、最终余量与总费用；未来收入不作为当前可花钱。
- [ ] 计划内费用预留、购买/恢复唯一操作、删除/改计划原子释放预留；余额不足/满体力/重复点不扣款。
- [ ] 免费休息支持零钱零体力；活动中原地安全停车也能恢复，不要求先走到商家；动作明确推进所有未完单600游戏秒，而非再乘120或点击倍率。
- [ ] 路段中途休息保存edgeId/方向/offset，后台或重载后完成剩余休息，再回原路段；最后一单完成只释放未执行补给预留，不回滚已发生支出。
- [ ] 服务中刷新/后台、补给支付后未恢复、恢复完成前退出、预留后改计划等都不重复收费或回满。
- [ ] 账单增加补给支出与净收益的独立口径，不改变“累计配送费”含义；旧档启用资源给满、不倒扣历史。
- [ ] 做普通选单、最差收益、连续餐损、零资源、三单极端绕路、多次免费休息、跨日等可重放模拟；再由用户验收节奏。

出口：零钱零体力能恢复→完成一笔单→获得收入；普通合理玩法扣必要补给仍为正收益；长路线不能在到补给点前卡死；错误计划提交前被拒绝；首次D+与城市现金门槛的真实单数/现实用时已记录。价格或消耗导致普遍亏损时先调数，不以广告救济替代平衡。

## 七、M5：经营、站点2与城市

映射旧T05–T07。功能：车辆/骑手实例、招募、独占配车、上岗/闲置、站点2、城市、多件/基础雨天、在线/半速/离线领取。NPC不要求逐个点击或补给。

- [ ] 县城达到100单并有现金即可升站点2；在县城先买C、招D，再免费进入城市。新快照放开已实现的站点与档位，不能被旧县城校验器拒绝。
- [ ] 招募/购买/升档检查目标档库存上限，车不重复分配，闲置不占车；玩家与NPC的完成单数、经验、线索分别统计。
- [ ] 正常在线P≤A×7/3、首次主动前半速、离线8小时/500单上限按真实时间分段；点击不多领，时钟倒退不发钱，同区间不重复领取。
- [ ] 完整NPC公式按收入倍率而非档位编号计算，最高已解锁地区、实际配车、评价与站点口径一致；同费率按小时与逐帧累计结果一致，保留不足一分余量。
- [ ] 资产/配车/评价/站点/城市变更先用旧费率结清；封顶等待→新增主动收入不能补发旧被截收益。离线先整体截8小时再跨日切分，500单上限只对整次领取应用一次，并消耗整个原区间游标。
- [ ] 同一未领取窗口中的费率变更不重置8小时/500单限额；领取上限参考值在窗口建立时冻结，不因领取前换车升级抬高。反复切换资产不能拆分旧区间多次应用上限。
- [ ] 雨天只在可用规则接入后出现，服务/时限/体力和补贴统一预估；多件影响实际载重，不提供全列表超载或必然失败的订单。

出口：从县城可自行满足城市条件；所需资产在县城可购，没有“先进城才能买进城必需车”；一名骑手配一辆独占车开始收益，重复领取/刷新无重复入账；正常主动收入＋补给＋被动上限账目一致。100单是最低资格，不作为必定攒够全部钱的承诺。

## 八、M6：省会、一线与更丰富事件

映射旧T08–T09。功能：站点3/4、工具B/B+/A、骑手到A、长途、保温、商务、上楼、垃圾、多需求、一线线索累计，以及有预兆/可应对的路况事件。

- [ ] 城市可先升站点3买B、配C骑手后解锁省会；省会可升站点4买A、配A骑手后解锁一线。
- [ ] 一线首次开放即接入线索资格快照、每单首次交付独立抽取、两类别累计/保存；预览/接取/撤回/NPC不发，累计3/6/9永久开资格，M7迁移原样保留。
- [ ] 温度按餐品取到后经历的游戏时间计算，不按动画秒数；点击快进不改善同计划温度，服务/补给时间计入。旧温度流失秒率先重新标定。
- [ ] 路况风险按已携带订单与真实路段处理，持久化阈值与事件；不按点击/帧数多抽，一单损坏不反复乘折扣。
- [ ] 新需求以弹窗选择，动作成本可预估；多项评价合并按单限幅，不能对超时、餐损或拒绝重复扣罚。
- [ ] 新重量/天气/保温/补给重新做最差可持续收益与可达性检查，仍保留普通可独立完成单；验证省会恢复感和一线难度节奏。

出口：逐级达标进入省会和一线、完成多需求订单；玩家能理解风险并做选择；至少有符合当前条件可按时/保温的路线，且连续坏结果仍有恢复路径。新机制与三单同屏不会遮挡核心操作。

## 九、M7：国际、隐藏终局与发行

## 十一、执行与交付约定

每个阶段按“明确参数/接口 → 有意义的失败案例 → 实现 → 定向及必要完整检查 → 类型/构建 → 独立复核 → 用户体验验收”推进。无需在同一阶段为每个文件重复索要批准，但本轮规划不等于自动开工授权。

数值记录至少包含：规则profile、种子/场景、每单收入/必要补给/净收益、体力轨迹、路线与载重、超时、首升/城门单数与现实等待。记录正常样本与极端边界，不把设计试算冒充概率实测或游戏回归。

全盘审查闭环与剩余验证见[审查报告](../../reviews/2026-10-29-delivery-game-v2-full-audit.md)。候选数值已验证可持续收入/恢复等安全底线；点按手感、NPC回本约6–12现实小时是否符合经营目标、国际强化与收集追求仍须对应阶段体验验证，不能只凭正收益就判定全部数值合理。

M3之后的代码级任务卡在前一阶段出口通过后展开；远期功能范围、依赖和验收已在本文固定，不提前编造未验证的UI和平台细节。任何尚未测的验收项保持未测，不因文档检查通过勾成已接受。
