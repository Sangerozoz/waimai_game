# 配送性能：已消费亲送事件的同步空操作

本批减少一类已复现的重复事务：当全部亲送完成事件已补入经营额度时，Fleet不再为无变化的同步重新序列化、恢复和复制整个钱包。只有事件游标与真实事件数**精确相等**才早退；存在待消费事件仍走原完整原子事务。改动仅一份生产源码，不改30Hz、速度、计时、补额金额、存档版本、旧合同或Runtime保存后发布流程。

当前状态：窄测、默认回归和typecheck通过；独立审查、Creator及预览部署待收口。本文件会在门禁完成后更新，不能将当前阶段当作已更新试玩。

## 复现与修复

原同步函数无条件执行`atomic`。新增测试先在未改源码上运行，6项因“10次已消费事件同步仍序列化钱包10次”失败，2项非法恢复测试通过；原始[RED](red.log)和[收据](red-receipt.json)保留。随后仅加入事件游标相等的早退，8/8通过。[GREEN](green.log) · [收据](green-receipt.json)。

kg与slots均覆盖空历史、已消费历史、真实恢复后的落后游标、后续新增事件及重复调用；每笔新事件仅补一次60000ms，现金与完整组合状态保持。越界游标和不一致完成数仍由原完整restore拒绝。序列化计数包装转发真实方法，不替换领域逻辑；无耗时阈值型单测。

## 同输入性能对照

[可重跑脚本](benchmark.cjs)分别在内存加载冻结before和实际after源码。现有长期模型终态为771笔亲送、884笔NPC成交；不重跑150分钟模型，不制造资金或更改存档。行驶态仅由同一终态经真实`pickup`、短tick、`continueTrip`导出，两版导出字节一致。原终态只读保留。

每个输入预热2对、记录8对，交替交换before/after运行顺序；每次均执行完整`restore → tick(1/30秒) → serialize → 完整restore`，然后逐字比较结果。四种输入共40对全等。

| 输入 | before完整事务中位ms | after完整事务中位ms | 降幅 |
| --- | ---: | ---: | ---: |
| 空新档 | 0.318 | 0.266 | 16.16% |
| 长期终态取餐 | 162.904 | 139.218 | 14.54% |
| 同源导出行驶态 | 162.806 | 137.502 | 15.54% |
| 原signedZeroQuota终态 | 1.468 | 1.226 | 16.55% |

长期行驶样本的tick部分为97.730→72.687ms；完整事务仍高于33ms。以上是本机Node内存候选事务，未计真实存储提交、UI绘制、GPU或远程网络，**不是FPS提升，也不关闭U01**。[全部原始样本与指纹](benchmark-result.json) · [执行收据](benchmark-receipt.json)。
