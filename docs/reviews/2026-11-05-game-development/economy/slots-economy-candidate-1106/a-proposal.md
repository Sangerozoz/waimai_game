## 4. 候选供给：不能把格数当成实际多接单

现成证据已读：`integration/user-existing-offers-readonly-1106.json`。旧池确为8条，1kg×4、2kg×4，总重12。

仅把相同的“4个1＋4个2”数列作**规划装箱算术**：

| 候选等级 | 初始车格数 | 该数列最多装餐数 | 比上级实际增加 |
|---|---:|---:|---|
| 1 | 2 | 2 | — |
| 2 | 2 | 2 | 否 |
| 3 | 3 | 3 | 是 |
| 4 | 3 | 3 | 否 |
| 5 | 4 | 4 | 是 |
| 6 | 4 | 4 | 否 |
| 7 | 4 | 4 | 否 |
| 8 | 5 | 4 | **否** |
| 9 | 5 | 4 | 否 |
| 10 | 6 | 5 | 是 |

**8级加1格在该池并不能多装一餐。** 这不能包装成每级容量都有兑现收益，更不能把旧kg合同直接转成slot。

当前还有两项明确供给限制：

- `normalCandidates`默认8；`Route.candidates:84-92`单次请求最多50，最多扫描`2×places.length`，不是无限供给。
- `Fleet.startBatches:73-76`县城还有2单硬截断。只改容量、不处理新规则下的NPC组单，4格以后很可能没有数量收益。

**必要接口候选：**

`candidatePage(cursor, limit=8) → { offers, nextCursor, exhausted, poolId }`

同一池固定扫描起点、ID及1/2格份量；滚动仅续扫既有有限范围，不重抽、不重置游标、不为填满背包无限生成。8/50是读取批量，不是持单上限；池耗尽如实返回。升级预览同时给出当前已知候选的装餐数前后值和`poolComplete`，未完整时不承诺容量收益。NPC新规则也必须使用有限供给，不能沿用“县城最多2单”再宣称大背包有用。

## 6. 必须冻结的跨模块兼容合同

1. **单位必须判别，不能rename：**  
   `Load = {version:'kg-v1', weightKg:number} | {version:'slots-v1', occupiedSlots:1|2}`；容量同样分别为`capacityKg`和整数`capacitySlots`。新slot订单不得夹带kg当业务输入；食品`food-risk-v1`保持独立，不往其严格三字段里塞容量。

2. **签约时锁完整条款：**  
   新合同锁`economyProfileId / pricePolicyId / effectPolicyId / Load / Capacity / level / speed / incomeFactor / serviceReduction`。运动、容量、NPC到期时间及结算都按该合同，不仅锁最后金额。

3. **保留旧数据，不伪装迁移：**  
   旧版本先过原完整校验；旧kg活单、NPC批次、报价、dueMs和历史收入原样完成。新批才采用slots。已有等级、金币、账本保留；未来升级只收新曲线的相邻等级费用，**不补收历史差额、不补发金币**。新资产格数按车型＋保留等级的新profile计算，不对旧kg值取整冒充转换。

4. **不能热换当前Config：**  
   当前恢复在`V2EconomySession.ts:81-124`校验固定configId，并复算锁定属性；全局替换`vehicleEffects/riderEffects`会使旧合同失败。候选需要双profile验证器，以及支持旧kg与新slots合同并存的新容器。建议冻结`Game6 / Route3 / Dispatch2 / Economy2 / Fleet2`及显式legacy分支；Trip3食品格式不因容量改名升级。版本组合须由PM整体冻结后实施。

5. **普通基费不涨：**  
   新slots不能自动代入旧`extraKg`。候选新报价版本只保留基础费、车辆/经验及可信距离差价；旧`ordinary-effort-v1`继续验证旧合同。不得重价在途单。

6. **NPC升级不能靠一刀切禁UI：**  
   V1:106允许工作中申请调整；现Dispatch全局batch禁令与Economy全局`idle()`需按对象重新审。候选为NPC升级确认后扣款、资产等级更新，已签批次仍按旧条款，新未签批次才生效；主角自己的活单换车/升级限制保留。此规则尚待PM冻结，当前guard没有改。
