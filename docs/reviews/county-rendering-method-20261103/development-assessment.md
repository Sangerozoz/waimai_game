# 县城街景渲染方法：开发只读评估

日期：2026-11-03。范围：针对用户拒绝的画面与已确认首页街景方向，评估首个街角样板的制作方法。本轮只读源码、本机安装和已有图片；没有改渲染代码、运行构建、测试、渲染或操作游戏和存档。用户最新画面反馈由 PM 转达；本评估另查看了此前被拒绝的样板截图及用户提供的目标街景图，不将旧截图冒充最新画面。

## 结论

是实现方法和美术生产流程共同造成了明显差距：现有样板更像“用坐标自动绘制的地图示意”，而用户要的是完成度较高的商住街景。当前方案能表达道路和建筑的基本空间关系，却没有具有身份差异的完整建筑资产、可靠的建筑材质体系和统一光照/遮挡体系。单纯增加密度、放大镜头、换通用贴图或调整颜色，不能补齐这些缺失。二维技术本身并非不能实现目标；真实 3D 也不会自动产生目标画风。

推荐下一步以 **Cocos 内真正的三维模块、固定斜俯视镜头和专门制作的风格化资产**做一个隔离街角样板，先解决视觉生产的核心问题，再决定是否适合扩展。这个建议是技术路线，不是已实现或已验证的结论；预渲染分层 2.5D 仍是可行备选，具体取决于资产生产、遮挡和可用性能。不要沿现有通用窗格算法继续叠补丁，也不要直接铺全县。

## 实际代码及差距的证据

- `delivery-game/county-sample/sample.js:1-7,35-50` 是独立 HTML 的 Canvas 2D 可视化；`ground()` 用固定仿射变换投影地面，`screen()` 把高度直接向屏幕上方平移。它有数学意义上的斜投影和建筑立面，并非完全没有投影；但没有三维场景的真实几何光照、深度缓冲和投影阴影。此处“没有真实投影”应理解为缺乏统一光照产生的真实投射阴影，而非没有二维坐标投影。
- `street-facades.js:14-20,24-49` 用相同的两种浅色墙面、按面长约 3.6 米切分的 bay、固定层高和相同上层图片反复铺墙；门面图片每个临街面只放在中央一格。建筑身份、柱廊、立面转折、檐口、材质层次、玻璃反射与店招都不能单靠统一公式自然生成。结果趋于重复小窗和统一盒子；目标图则有有层次的商铺、较大玻璃、雨棚、不同墙面与屋顶设备。
- `street-facades.js:14,49-66` 阴影是地面轮廓统一平移后填色，面色用朝向条件选两种预设色；设备只由简单几何绘制。无法随着建筑高度、灯光方向和邻近物体生成协调的遮蔽、接触阴影和明暗渐变。屋顶/墙体仍是二维多边形及图片，并非具备体积材质的三维模型。
- `sample.js:112-127` 先以米灰基底和地块色铺面，道路以线段宽度的多边形铺设，建筑/树/骑手依地面代表点排序后绘制。该排序可处理一部分前后关系，但不能普遍正确处理大型不规则建筑、树和骑手相互穿插及阴影遮挡。固定底色与低透明纹理也容易形成平整沙盘感。用户指出的空地和绿地问题还与具体场景数据、地块安排有关，不能只归咎于渲染器。
- `delivery-game/assets/scripts/map-sample/CountySampleBridge.ts:3-24` 在 Web 情况下可选创建 iframe，约每 0.25 秒向独立样板发送骑手、路线和站点数据；它不是把该样板变成 Cocos 3D 场景。原游戏地图另在 `CityMap.ts` 使用 Cocos 的 Graphics、Sprite 等。桥接是只读显示方向，不能据此声称实现场景整体迁移或用户体验已验收。
- 目标参考中近景街角具有独立设计的建筑体量、商铺玻璃与雨棚、人行道细节、受光面和投射阴影；此前被拒截图是大范围重复建筑与较多空白地块。截图与当前源码属于不同时间点；以上从现有代码推导的问题是可核对的技术限制，画面改善幅度仍须在授权的视觉反馈阶段确认。

## 三条路线比较

| 路线 | 如何达到目标、仍需资产 | 任意足迹/路网及动态对象 | 成本、性能与风险 |
| --- | --- | --- | --- |
| ① 继续二维逐面绘制 | 需要由美术设计多套完整立面、转角、屋顶、地面细节及统一受光/阴影规则，并改进分层遮挡；用原代码上的通用窗格重复并不足够。高质量二维完全有可能达到目标。 | 可继续复用足迹和坐标；不规则边、多方向建筑需要可组合或专门绘制，转角与遮挡处理复杂。路线仍用原世界坐标，人物需分层遮挡。 | 既有框架改造量相对小，但高品质美术、排序和特殊地块的人工作业可能很高；Canvas 多对象重绘在目标设备上的性能未知。通用规则越多，越容易再次呈现程式化。 |
| ② 固定机位预渲染/分层 2.5D | 先制作并统一渲染有体块/材质/光照的楼、道路和街景，再输出带透明边界、锚点和分层信息的图片；也可手绘。需要多套地面、建筑前后层、树和道具及一致的阴影。 | 固定角度最合适。可按地块和对象分层、锚定原坐标；任意不规则足迹及建筑的拼缝、道路形状、骑手穿过前后遮挡层需专门适配，不能用整张不可交互大图替代路网。 | 运行时通常可较省几何成本，但纹理尺寸、内存、图集、遮挡切片和缩放清晰度需验证；可复用程度受镜头与形状限制，新增变体有生产成本。 |
| ③ Cocos 内 3D 模块＋固定斜俯视机位 | 需真正制作有差异的商住楼模块、路缘/铺装、店面/遮阳棚、屋顶设备、路灯/树和贴图，统一材质、主光、环境光与阴影；可用正交或长焦透视固定镜头，以视觉样板定参数。三维不是自动等于目标风格。 | 三维体块/模块可按原坐标放置，深度关系更自然；任意凹多边形、狭长楼、曲道路口仍需适配和人工检查，不能强行缩放扭曲或改变路网。地面高度、相机投影、角色排序/遮挡、屏幕映射要明确。 | 模型、UV、材质、灯光和场景集成的前期成本较高；网格数量、draw call、贴图内存、阴影和移动设备帧率需实测，不能预言更快或更慢。可通过模块、合批、简化阴影和分区加载控制，但这些尚未验证。 |

- 本次查看 `/Applications` 和 PATH，未发现 Blender 应用或 `blender`、`assimp` 命令；未安装或联网下载任何工具。此为本次有限范围核对，不排除其他路径存在软件。Cocos 的基础场景/几何编辑可作为搭样手段的候选，但不能据此宣称已具备完整建模、UV、贴图与复杂资产生产能力。
- 在仓库中查找常见 `.fbx/.gltf/.glb/.obj/.blend` 文件，只发现另一个示例工程临时缓存中的 glTF，未发现可直接用于本项目的成熟商住街景 3D 模块库。现有 SF01/SF02/RF01 等是二维图片候选，不等同三维建筑资产或已验收的材质；树及骑手图片可作为候选参考，是否适用新的机位、遮挡及光照需另行确认。
- 本轮没有渲染、重现测试或运行反馈循环，且用户明确要求阶段完成后集中测试；因此以上是基于源码、已有画面和人工检查的技术分析，因果推断有待后续样板视觉观察验证，并非已测得的性能或视觉结论。

## 建议的隔离视觉样板

1. **锁定范围与数据**：在已认可的榕树街食堂—晴川广场首块内选一个真实街角，读取原有道路中心线、路宽和附近三个建筑足迹。镜头先固定，样板仅展示该街角；不修改 `city.json`、道路拓扑、路线、经营逻辑、碰撞与存档，也不触及五张地图选择卡的产品结构。原建筑足迹若无法容纳所需完整体块，应标注局限并单独设计可适配模块，不能悄悄移动路网。
2. **生产三栋有身份的建筑**：一栋转角商铺（大窗和橙色雨棚）、一栋相邻较朴素商住楼、一栋具有不同立面/体量的街边建筑。针对现有足迹手工选配或局部裁切模块，不能用同一立面铺三遍；明确尺寸、地面锚点、入口朝向、遮挡层、材质和屋顶设备。风格以已认可首页和用户目标街景为准，控制蓝色与地面绿量，不在屋顶种树。
3. **补齐街道与统一光照**：只做一段道路及连续人行道、路缘/人行横道、少量路灯和地面树，加入一致的主光、环境光、接触/投影阴影；明确树和建筑与路面、骑手的深度关系。素材必须来自专门制作或明确授权的资源，当前没有成熟模块库，不把几何白盒当成成品。
4. **接回真实坐标**：定义游戏平面 `(x,y)` 到引擎地面 `(X,Z)` 的固定比例、原点和轴向，建筑高度走引擎 Y；所有视觉对象和路线只读使用相同坐标。单独记录相机参数、镜头范围及地面锚点。现有 `OrderBook`、路由、定位和存档仍为唯一权威，显示层不得反写数据。现有 iframe 桥可保留作为历史/对照，但 Cocos 内样板需明确新的只读数据接口，不能假称现有桥已完成 3D 迁移。
5. **先对齐再扩展**：按用户已确认参考观察建筑辨识、玻璃/墙体、街角密度、光影、骑手与物体遮挡，再决定是否扩成模块库。此处为后续视觉审核标准，不是本轮已做的渲染或测试；游戏测试仍仅在用户明确“阶段完成”后组织，体验验收由用户决定。

可保留：原始路网/地点/路线/经营数据、三层边界和样板坐标、已有规划与二维候选素材及其来源、只读桥接思路、当前旧样板作为技术对照。不能默认复用：重复窗格算法作为成品建筑、无明确许可/质量确认的第三方模型、固定阴影偏移作为统一光照、未经验证的性能或美术验收结论。
