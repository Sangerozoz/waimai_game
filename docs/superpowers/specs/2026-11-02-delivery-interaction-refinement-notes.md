| 体力耗尽 | 配送途中体力为0时原地停止；吃喝恢复后继续；没钱可以免费休息，但耗时更长，订单可能超时 | 用户明确选择A；不采用零体力低速继续配送。恢复量、具体耗时仍待阶段数值设计 |
| 配送结算呈现 | 逐单简短反馈、整批完整结算；每单送达立即入账，简短显示收入、准时情况、餐品状态、顾客评价，无需点击确认；全部送完展示整趟收入、补给支出、净赚及经验 | 用户明确选择A，覆盖逐单强制完整弹窗方案；不改具体奖励与处罚数值 |
| 取消配送 | 取消本趟全部未完成订单，结束本批并回到首页，保留当前位置；已完成订单收入/经验保留，未完成订单不发奖励，不额外扣钱或评价，已花补给不退 | 用户明确选择A；不提供本轮逐单取消并重排余单的分支 |
| 成长任务 | 存钱及资格满足时提示前往招募/买车/开图，实际完成后给部分金币或补给品奖励 | 用户明确要求；具体目标组织与奖励参数为PM推荐，见下方专案 |
| 地图支付 | 开放新地图需要支付金币，同时满足订单量或团队建设条件 | 用户明确选择付费方案，覆盖此前PM免费开图建议；具体门槛/费用候选待统一审阅 |

用户本轮没有批准挂机上限具体金额、上线即重置、日重置、亲送补充额度或原8小时/70%候选。收益上限恢复机制需单独沟通，不能默认打开游戏即可无限刷新额度；不恢复旧500单等历史上限。

补给的阶段提升应落实为体力需求/可选商品/成本变化，不能把“吃喝概率”实现成随机禁止玩家补给。是否强制淘汰便宜补给尚未确认。风险和成本要与同期收入一起校准，目标为进度带来更丰富的经营选择。

## 2. 已明确的选单与选路片段

大厅显示当前配车容量、已选订单数、累计重量和预计收入。每次添加前按实际精度计算“已选总重＋新单重量≤容量”；等于容量允许，超出则阻止添加并说明还剩多少容量。不使用UI取整后的数字判断，也不再显示“2/3”。不因没有固定单数上限而取消重量校验。

例：容量5kg，已选两个2kg订单，占用4kg；可再加1kg订单，不可再加2kg订单。此例只解释容量，不锁定实际订单重量或车型数值。

进入路线页后，系统为这一批订单安排合法的先取后送顺序，提供快捷/均衡/平稳方案。每套应显示整趟预计路程/耗时、各单预计到达与超时风险、餐损风险和体力需求。容量允许不等于保证准时；物理不可行方案不能提交，超时高风险方案的确认方式尚待具体设计。

选择后出发，本批订单固定，途中交付只释放车内负重、不开放接新单。全部完成，或主动取消全部未完成订单结束本批后，才可开始下一批选单。大厅展示的候选数量可以分页/刷新，不以旧“约10单”候选池变成新的隐性持单上限。

“快捷”优先耗时，“平稳”优先低颠簸/低餐损，“均衡”综合；差异来自真实道路与取送次序，不能保证任何地图/订单组合都必然有三条不同可行方案。无差异时合并或标识相同的呈现建议待后续细化。

### 体力为0后的恢复

用户已确认：体力耗尽后停止行驶，保留当前位置和本批订单；通过吃饭/喝水恢复后继续，没钱仍可原地免费休息恢复，休息比付费补给耗时更长，可能使未完成订单超时。恢复后从停下的位置续送，不重新起跑、不抹掉已经完成的配送结果。此规则针对玩家亲送，不扩展为逐个手动照顾NPC。

PM呈现建议：提示“体力耗尽”，展示可用补给的价格/恢复量/耗时及“免费休息”入口，不自动扣费。实际恢复动作的耗时影响同批所有未完成订单。具体补给及休息时长、恢复量、选择面板期间的计时状态继续统一细化；未因本次选择批准旧表中的秒数。

### 逐单反馈与整批结算

用户已确认：每单送达立即入账，显示收入、准时/晚到、餐品完好/损坏和顾客评价的简短提示，不要求点击确认，不额外阻塞后续配送。最后一单送完后，展示整批完整结算：本批配送收入、实际补给支出、配送净赚和经验汇总。

账务约束：每单仅结算一次，汇总读取已经发生的结果，不再发一遍金币或经验；补给按本批实际消费仅计一次，不能在各订单和汇总处重复扣款。简短反馈本身不额外触发暂停，不改变已有到点取餐/去配送等操作；主动展开详情的计时规则另行统一。取消收尾按下一节执行，不把取消记为整批全部送达。

### 取消整趟未完成配送

用户已确认：主动点击取消配送时，取消本批全部未完成订单，结束本趟，回到首页并保留当前道路位置。已经完成订单的收入与经验保留，不重复结算、不追回；未完成订单无配送费、经验或其他完成奖励。不额外扣钱或评价，已经消费的补给不退款。

取消结束活动批次后可重新去大厅组下一批，不保留隐形的未完成单占用容量，也不将它们计为完成单量。此前已完成单及真实补给支出继续保留在账单中。已完成订单本身不可取消；正常配送中的未完成批次仍按现有保存/暂停边界处理，取消按钮显示阶段和存档续送细节另行汇总，不擅自将关页面等同于取消。
