# 配送玩法增强整体汇总

> 本讨论已整理为[V2整体设计与数值约束](2026-10-28-delivery-game-v2-design.md)和[七阶段实施方案](../plans/2026-10-28-delivery-game-v2.md)。下文保留讨论来源，后续规则与阶段出口查阅新版；新功能尚未实施。

2026-10-28。来源：本聊天对自动配送参与感、补给经济、多单规划的讨论，以及用户补充的连续点击加速。

**状态：后续方案汇总，未进入开发。** 本文区分用户明确方向与推荐规则，不将建议当作已确认需求，不修改当前可玩版参数或验收结果。

## 1. 方向与确认程度

| 内容 | 状态 | 含义 |
| --- | --- | --- |
| 保留自动行驶动画 | 用户明确 | 去商家和去顾客都自动沿道路移动，当前不改为完整手动驾驶 |
| 拉长基础配送表现、增加点击加速 | 用户明确 | 不操作按载具基础速度完成；点击越快、越多，加速越明显 |
| 基础约10秒、密集点击约3秒 | 用户举例，待调数 | 说明参与前后的等待差异，不要求每段距离都固定10秒或3秒 |
| 取送环节补充操作 | 用户确认要完善方向 | 具体按钮与到点确认流程属于下述建议 |
| 加入体力与喝水、吃饭补给 | 用户确认后续考虑 | 具体体力、价格、恢复量和耗时未定 |
| 多单与顺路规划 | 用户确认后续考虑 | 建议首版上限3单，先出发前组单，再考虑途中接单 |
| 点击对时限、体力、风险的影响 | 待确认，本文提出推荐 | 推荐先做玩家行程快进，保留路线策略；不额外扣体力或加餐损 |

体验目标：玩家挑选合适的订单组合、安排取送顺序、通过点击缩短现实等待、在地点完成交互，并决定何时补给。多单与补给提供取舍，点击与音画反馈提供即时参与。

## 2. 完整体验流程

大厅查看订单 → 接1–3单 → 查看绕行、预计送达与载重 → 安排停靠顺序 → 出发自动行驶 → 可点击加速 → 到站取餐/交付/补给 → 前往下一站 → 逐单结算 → 全部完成后继续接单。

同一行程中，交付一单立即结算这一单并继续剩余任务。结算回执不应每送一单都强迫返回大厅或结束整趟行程。

## 3. 自动行驶、点击加速与停靠操作

### 用户已明确的部分

- 去商家、去顾客均自动沿真实道路移动，无需方向盘或摇杆。
- 基础动画节奏加长，以便玩家看清路径并有时间操作；载具升级仍改善基础速度。
- 只有行驶中显示加速按钮。连续点击越密集，进程越快；不点击也能完成。

### 推荐的首版规则

- 每次有效点击积累短时加速，连续点击叠加，设有限上限；停止点击逐渐回到基础速度。按钮与拖图分离，不把地图点击误判成加速。
- 以某段路基础约10秒、充分点击约3秒作为试验例子。基础时间取决于道路距离和车辆，所有车辆共用受控加速规则，不给每段路固定同样时长。
- 点击先理解为**玩家行程快进**：实际道路、游戏配送分钟、体力消耗和每单最终时限结果不因播放更快而凭空改变。行驶和同一行程中所有订单的配送时钟一起推进。
- 快进只影响玩家当前行程，不加速账单前台在线时长、本地日期、每日刷新、离线收益或以后NPC骑手的经营计时。
- 首版建议点击不额外扣体力、不提高餐损概率，防止形成必须狂点才能正常经营的压力。真正提高游戏内速度、改变准时率的“冲刺”如有需要，另行设计代价与上限。
- 加速上限、叠加和衰减、基础时长均需样板调数；不新增无上限速度或单击直接送达。

### 推荐的到点交互

- 到商家停下，点一次取餐，播放现有2秒取餐动作，再按计划前进。
- 到顾客停下，点送达；有放门口、以后上楼/带垃圾等需求时在弹窗处理，随后结算该单。
- 同一家商家的多单可一次取餐操作处理；每单仍独立变为已取餐，避免重复点击。
- 到点手动确认属于建议，用户本次确认的是自动动画与加速，不能据此默认额外确认次数已定。
- 现有到店2秒动作首版建议固定，不受行驶加速压缩。是否加速服务动作可后续验证。

点击要有即时按压、车速变化和声音反馈；松手仍可完成。正式图标沿用用户提供资源的约定。是否有趣需验证，不能以点击次数多作为成功标准。

## 4. 多单规划

- 建议最多同时持有3单，也可只接1单。首版出发前组单，不一开始加入途中派单。
- 订单大厅与已接订单分开管理，同一张订单不能重复接取。
- 每单必须先取餐、后送达；商家与顾客最多形成6个任务停靠点。规划按真实有向路网计算，不能以直线距离代表顺路。
- 接新单前预览新增绕行时间、加入后每一单预计送达时间、可能超时的订单，以及各取餐点之后的车上重量。
- 每单时限在承诺时确定，追加订单、改顺序、刷新、加速都不能重置旧单时限。单独可按时的订单，拼在一起可能超时，由预览告知玩家取舍。
- 载重按车上实际携带餐品检查。同路三单不因接单总重量被机械拒绝，也不能因为每张单独不超重就忽略同时取齐后的超载。
- 超时订单仍能完成，按各自规则评价、结算；一单超时不取消其他订单。
- 到点动作、需求、结果和回执均按订单保存。不是把三单合成一笔统一奖励。

后续开放途中接单时，再加入剩余停靠点重排、候选重筛和在途承诺预估。第一版不提前扩大到这部分。

## 5. 体力与补给

- 建议先只用一条体力值；喝水是较小恢复，吃饭是较大恢复。暂不同时做饥饿、口渴、疲劳三条数值。
- 体力消耗以实际行驶距离为主，取送动作增加少量消耗。同路携带三单，共同行驶路段只扣一次行驶消耗；点击快进不按点击次数或现实动画秒数扣体力。
- 接单规划时预估完成行程所需体力，并允许插入补给停靠。首版可利用现有商家附近补给，不先增加复杂背包和大量新地点。
- 补给有明确价格、恢复量及游戏内耗时；其耗时影响所有未完成订单的预计送达。思考菜单本身不收费、不暗中耗时。
- 低体力效果需验证，避免叠加严重减速、高事故率和高补给成本；需要免费休息等恢复方式，防止低余额后无法继续赚钱。
- 不操作加速也应能正常完成合理行程并获得成长。普通跑单扣除必要补给后应有稳定净收入。
- 新增费用意味着初期攒钱、200元换D+、城市100单等经济节奏需要重新验算，不自动修改已定价格、也不预先许诺具体单数。

价格、恢复量、消耗率、免费恢复耗时、低体力效果均未定，需要在行程玩法成立之后调数。

## 6. 时间、事件与账单统一口径

| 时间或进度 | 用途 | 点击加速的建议影响 |
| --- | --- | --- |
| 现实前台在线时间 | 当前账单在线时长、后续在线经营 | 保持实际时间，不能虚增 |
| 玩家行程的游戏配送时间 | 各单预计送达、时限、补给与路程成本 | 与行程进度一起快进，同一行程的订单共用 |
| 动画表现时间 | 现实里等待几秒、车辆运动和动作反馈 | 连续点击缩短行驶等待，服务动作可独立配置 |

- 出发前规划、阅读选择弹窗沿用不扣配送时间的方向；执行行驶、补给等行为才推进明确游戏用时。暂停用于思考，不等于消除动作代价。
- 系统后台仍冻结配送并保存；恢复不能重置时限、重抽结果或重复发奖。
- 现有取餐2秒是表现等待，服务占用多少游戏分钟必须独立规定，不能按原压缩比机械折成6分钟。
- 原“30分钟=10秒、最多15秒”是当前版本规则。新玩法需要重调基础表现节奏，确认后对新规则版本替换；不能让每一张订单或每一段路独立封顶而破坏同一行程时钟。
- 加速跨过路段也必须依次处理餐损事件、到站和交付，不能跳过必须停靠的地点。
- 未来可应对的颠簸/雨天事件应按真实路段触发，只影响当时车上的餐品；还未取、已经送达的订单不受影响。点击频率、帧数本身不能增加事故抽样次数。
- 逐单结算登记配送费、经验、好差评、准时/超时；骑手实际行驶的共用里程仅统计一次。补给支出另记，区分配送费与净收益，不改写历史账单。

## 7. 现有框架如何接入

| 部分 | 当前基础 | 建议改动 |
| --- | --- | --- |
| 订单管理OrderBook | 一张AcceptedDelivery同时承担订单与移动状态 | 保留统一操作入口，内部区分1–3张订单、骑手当前行程和地点动作 |
| 行程与停靠点 | 单单的取餐点→顾客点 | 增加有序停靠任务，区分当前行驶段、到点等待、取餐、交付、补给 |
| RoadRouter | 真实道路寻路、不同道路偏好 | 复用各段寻路，增加多停靠顺序的合法性、ETA与绕行预览 |
| DeliveryClock | 单条路线时长与动画进度 | 拆清现实在线、统一行程时间和表现时间；加速不能散落在每个订单里各算一遍 |
| 车辆与体力 | 载具基础速度、载重和收入倍率 | 基础车速、玩家点击倍率分别管理；体力与补给在独立规则中处理 |
| CountyRules结算 | 单单的玩家快照与结果 | 每单冻结应冻结的车/等级参数，余额、经验和评价在交付时按当前状态连续更新，避免多单覆盖旧钱包 |
| 餐损事件 | 出发固定结果、送餐中段提示 | 如要让玩家应对影响结果，另扩展路段事件与已携带订单的结果状态；旧单仍保留旧规则 |
| DeliveryLedger账单 | 单次完成登记费用与路线里程 | 收入逐单登记、共享里程按实际行驶登记，增加补给支出，维持防重与本地日切 |
| CountySnapshot/SaveStore | 当前活动与进度兼容恢复 | 保存订单列表、停靠计划、已携带餐品、各单期限/结果、行程进度和体力；旧单迁为一单行程或按旧规则完成 |
| MapSample/OrderPhone/CityMap | 地图主页、候选大厅、活动面板 | 保留现有导航与精简文案；增加行驶时加速按钮、组单与规划面板、地点操作、补给弹窗 |

只暴露清楚的玩家操作：接单、调整计划、出发、加速、取餐、交付、补给。合法性、计时、结果、计费由内部规则负责，UI不自行扣体力或加钱。

存档只保存业务进度与必要结果，不保存每次点击历史。重载后可回到基础加速状态，但实际路程、期限、体力、已领奖状态不回退。

## 8. 与原阶段安排的关系

原三大阶段继续保留：县城主动配送 → 第二阶段经营/扩张 → 第三阶段国际/隐藏/终局。

建议在当前第一阶段收尾和第二阶段经营扩张之间安排“核心配送玩法增强”，按三个可独立验证的增量交付；这只是建议排期，不自动开启开发，不取消已有验收结果。

1. 自动行驶的基础节奏、点击加速、到点交互与必要音画反馈。先一单验证参与感，保留当前经济规则。
2. 新行程模型与最多三单规划，验证顺路选择、独立时限、载重、共享里程和逐单结算。
3. 体力、补给和净收益平衡，验证正常游玩、低余额、低体力及连续坏结果仍能继续经营。

之后再继续骑手/站点/城市等原经营路线。点击加速先只属于玩家主动配送，不要求为未来每个招募骑手逐个点击，也不自动把玩家补给机制复制给所有NPC。

## 9. 验证与尚待决定事项

| 增量 | 重点验证 |
| --- | --- |
| 点击加速 | 不点能自然完成，点击有即时反馈且有上限；10秒→3秒的差异是否舒服；是否变成重复手指劳动；不跳站、不重抽、不改变账单在线时长 |
| 取送交互 | 到点操作清楚、同店多单不重复点；自动与手动环节不会造成卡住误解；2秒动作可辨认 |
| 多单 | 顺路组合节省实际里程/体力；绕路的高价单可能不值得接；预计送达与实际一致，分别结算不丢钱 |
| 补给 | 常规收入扣除补给仍可成长；低体力/低余额有恢复路径；加速和拼单不会重复扣同一路段消耗 |
| 整体 | 刷新与后台兼容；更快现实完成单数对200元升级、100单等门槛的实际节奏影响；玩家愿意主动规划而非被迫多点 |

待确认的设计选择：点击是否只快进或真的改变游戏内车速；到点确认方式；基础时长与加速上限；2秒取餐是否加速；补给价格、耗时、消耗和恢复；多单开放时机与取消规则。上述未定项不阻止完成本轮汇总，但正式实施前需形成明确规则。
