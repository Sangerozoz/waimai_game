# 亲自配送：多单、选路、事件、结算与随时补给

最新交互决定与待沟通场景见[2026-11-02方案收口记录](2026-11-02-delivery-interaction-refinement-notes.md)。取消最多3单，按本批总重限制添加；只在大厅组单，出发后不加单、全部完成再接；系统给快捷/均衡/平稳方案并安排取送顺序。前期低风险低价补给，后续概率与吃喝花费逐渐提升，具体参数待定。

## 1. 用户已确认

| 内容 | 当前要求 |
| --- | --- |
| 接单入口 | 抢单大厅 |
| 同时持单 | 不设固定接单数量上限，本批已选总重超过车辆容量不能添加 |
| 接单时机 | 大厅组好一批，出发后不加单，全部送完再接下一批 |
| 路线 | 系统给快捷、均衡、平稳三套方案，自动安排取送顺序，玩家选择一套 |
| 途中事件 | 下雨、恶劣天气、路程颠簸、餐品损坏、红灯等因素 |
| 超时来源 | 途中事件、接单较多等因素可能导致订单超时 |
| 送达结算 | 根据送达后的反馈给出结算画面；具体反馈项目与算法继续细化 |
| 体力 | 配送过程中有体力值，低体力需要吃饭、喝水补给 |
| 补给位置 | 用户选择随时点击补给按钮，主要管理费用与体力；不要求去指定餐馆或商店，不增加找店绕路 |
| 阶段变化 | 早期雨天/餐损低频、补给便宜，逐渐提升风险与吃喝花费；纯净水/泡面到饮料奶茶/快餐/高档餐食 |
| 体力为0 | 原地停止配送，吃喝恢复后继续；没钱可免费休息，但耗时更长，可能超时 |
| 结算呈现 | 每单送达立即入账，收入/准时情况/餐品状态/顾客评价简短反馈，无需确认；整批送完展示收入/补给/净赚/经验汇总 |
| 主动取消 | 取消本趟全部未完成订单并回首页、保留位置；已完成收入/经验保留，未完成无奖，无额外扣钱/评价，补给不退 |

本稿聚焦玩家亲自配送。自动骑手是否另算体力和补给成本尚未确认，不自动扩展为30名骑手逐个操作。

## 2. 完整流程

**抢单大厅 → 在容量内选好本批订单 → 从系统推荐方案选择路线 → 出发取送（不加新单） → 应对事件与体力变化 → 按需点击吃饭/喝水 → 逐单送达结算 → 全部完成后接下一批。**

| 环节 | 玩家能做的主要选择 | 需要看清的信息 |
| --- | --- | --- |
| 选单 | 容量内选一单或多单，考虑方向是否相近；超出不能添加 | 商家/顾客位置、配送费、各单时限、餐品重量、已选总重/容量 |
| 选路线 | 权衡耗时、绕行与路面风险 | 各单预计到达、总路程、预计载重及体力需求、已知天气/风险 |
| 行驶取送 | 沿所选路线推进，处理必要到点操作 | 当前目标、各单剩余时限、体力与事件反馈 |
| 补给 | 随时通过按钮吃饭或喝水 | 费用、恢复量、补给后体力；若设计耗时须提前说明 |
| 送达 | 查看本单交付结果及反馈 | 实际到账、评价/经验及影响原因 |
| 续送/续玩 | 有余单继续，全部完成后再接单 | 剩余订单、当前地点和体力、整趟支出与净收入 |

除用户已确认条目外，表中具体字段、呈现与顺序是PM建议，尚未实现。现行“手动取餐及去配送、顾客端自动结算”的操作作为既有参考，本轮未据新描述擅自更改按钮或重新启用需求问答弹窗。

## 3. 多单应产生的取舍（建议）

- 顺路组合可以共享行驶路程、提高一趟总收入；绕路组合增加后面订单的超时风险。
- 每单保留自己的承诺期限、餐品状态和结算结果；多单不代表一起超时或一起损坏。
- 推荐路线应展示各单ETA，而不是只显示全趟总时长。大厅先按本批总重限制添加，出发后每单先取后送并维护实际负重；不能用先送后取绕过大厅总重限制。
- 同一路段的里程和体力只计算一次，不乘订单数量；取餐/交付动作是否分别消耗体力需明确。
- 超时风险高可以预警；不能用多接单就固定触发惩罚代替真实行程计算。
- 已取消3单上限，大容量可容纳更多订单或更重订单；不将容量直接乘收入，也不额外偷偷设另一个单数上限。

## 4. 偶然事件如何作用（建议）

| 因素 | 建议作用 | 对玩家选择的意义 |
| --- | --- | --- |
| 下雨/恶劣天气 | 改变道路耗时或增加特定风险；严重程度需分层 | 已知天气提前说明，临时变化给可理解的提示 |
| 颠簸路段 | 增加已取餐订单的餐损风险 | 较近的路可能更颠簸，平稳路线可能更远 |
| 红灯 | 增加明确的停等时间，影响未完成订单ETA | 红灯较多路线与其他路线有耗时差异 |
| 餐品损坏 | 作为路况/天气等风险的交付结果 | 影响实际交付反馈与收益，不重复抽取无来源处罚 |
| 多单绕行 | 由实际取送顺序和服务时间形成延误 | 收益增加与时限压力形成真实取舍 |

已有天气、道路风险尽量在出发前可见，突发事件保留不确定性，但单趟影响应有边界，不连续无上限叠加重罚。餐损只作用于已经取到且尚未交付的餐品；不按点击次数、帧数重复抽损坏。

红灯、天气、绕行造成的时间推进应影响同趟所有未完成订单，不能只扣当前目标的时间。各单反馈应能解释准时/晚到、完好/损坏，避免另外再给无依据的随机差评。

超时后建议仍可完成配送，以评价和合理的收入变化表现后果；不把普通超时自动变成整趟失败。具体扣减、上限与概率待数值设计，未直接恢复旧参数。

## 5. 体力与随时补给

**用户已选择：不寻店、不绕路，随时点击按钮补给。** 此条覆盖旧V2中计划内补给地点、到店可达性及绕路补给的冲突安排；不因此增加背包、库存或食物制作系统。

用户新增阶段成长：前期纯净水和泡面，后续饮料/奶茶、快餐、高档餐食，吃喝花费逐渐增加；前期需求较低，后期随进度提高。具体售价、恢复量、耗时、便宜补给能否保留尚未确定，不据此随机锁住补给按钮。若补给占时间，应提前可见并纳入全部未完成订单时限。

实际行驶距离和取送动作决定体力消耗；接单、阅读、查看结算不应因玩家读得慢而额外扣体力。用户已明确选择：途中体力降到0时原地停止，吃喝恢复后继续；没钱可以免费休息，但耗时更长，订单可能因此超时。保留停下的位置和剩余订单，恢复后续送。

补给/免费休息的具体耗时、恢复量、服务中能否操作和选择面板期间的计时规则仍待统一设计；不能将确认有时间代价理解为旧表具体秒数已通过。实际恢复动作影响同批全部未完成订单，不只影响当前一单。

## 6. 顾客反馈与结算（呈现已确认，数值待细化）

将用户所说送达后的反馈先理解为交付结果/顾客反馈，具体互动是否需要玩家选择尚未确认。

用户已确认采用逐单简短反馈、整批完整结算。每单送达立即入账，简短显示收入、准时情况、餐品状态和顾客评价，无需点击确认；有余单继续按既有取送操作推进，不额外用完整结算弹窗阻塞。全部送完后展示整趟收入、补给支出、净赚及经验。

补给支出按真实消费只记一次；餐损或晚到的展示扣减解释实际到账，不再次扣款。整批汇总读取已发生结果，不重复发钱或经验。简短提示自身不触发额外暂停，主动展开详情的计时细节另定。

取消配送已确认：取消本批全部未完成订单，结束本趟并回首页，保留当前位置。已完成收入和经验保留，未完成不发奖励，无额外扣钱/评价，补给不退款。取消订单不计完成单量；本批结束后可以重新去大厅组单。关闭游戏、保存及恢复仍单独遵循存档续送规则，不视为主动取消。

## 7. 对现有经济候选的影响

基础配送费仍为10元。当前[30名骑手版联合定价](2026-11-01-vehicle-and-rider-pricing-v2-30-riders.md)算的是标准参考毛收入；加入体力补给、超时和餐损后，需要补充实际净收入场景。

- 首次招募参考的“再跑15单”成立于每单净得10元且无额外支出，不是加入补给和事件后仍固定不变的承诺。
- 旧V2按基础费15元算出的最差可持续收入及水2元/饭5元价格，不能直接当作10元基础费的新平衡结论。
- 后续同一参数包应包括：各类路线耗时/风险、事件概率及延误边界、每单期限、体力消耗、水饭价格/恢复量/耗时、交付反馈及收入变化。
- 普通合理选单应在必要补给后仍可持续成长，免费恢复路径不依赖广告；极端组合和坏运气需给明确后果与恢复方式。
- 自动骑手若后续也计算补给，必须把自动补给成本与产能一起并入净收益，不能只增加名义收入而沿用旧毛回本结论。
