# 工作模板与拆解方法

按当前请求选择模板，复用已有材料。模板是建议结构，不要求每个项目生成一套相同文件。

## 1. 概念说明：从想法走到可讨论的方案

通常一页以内，回答：

- 目标玩家、设备、游玩情境，以及人员、时间和资源约束。
- 玩家反复执行的动作与选择。
- 希望产生的体验，以及玩家愿意继续的原因。
- 完整一局如何开始、推进、结束、重来。
- 当前版本必须保留、可延后和明确不做的内容。
- 最没有把握、可能改变方向的假设。

决定表区分事实与建议：

| 条目 | 内容 | 状态 | 来源或验证方式 |
| --- | --- | --- | --- |
| 平台、规则、体验等 | 当前描述 | 已确认 / 假设待验证 / 建议 / 待决定 | 用户指令、参考、实验等 |

原型中暂用的数值标成临时配置；示例不自动成为需求。

需要通过实验回答的问题应写进方案，不要求先在纸面上得出结论。胜负、进度、续玩和恢复方式按游戏形态选择，不要求所有游戏都存在失败或关卡。

## 2. 可进入开发的方案

以能指导制作和验收为准，覆盖：

- **体验流程**：玩家看见什么、输入什么、系统改变什么、获得什么反馈。
- **规则与状态**：目标、限制、胜负、暂停、重来及关键边界情况。
- **交付形态**：引擎或技术栈、浏览器或客户端产物、目标设备与操作方式。
- **内容与资源**：场景、角色、UI、音频等实际需要的资源；哪些占位、哪些必须有代表性。
- **技术边界**：模块职责、状态由谁持有、交互或数据契约、资源如何接入。
- **范围与证据**：当前版本取舍、未验证假设、可观察的验收标准。

方案可以先是草案，实验后再修订。已有代码时先了解现状，保留可用部分；技术选型改变要说明收益和迁移成本。

## 3. 关键未知：将模糊问题变成实验

实验卡包含：问题、假设、最小实验内容、需要的代表性资源、时间预算、观察指标、成功与失败后的决定。

「验证好不好玩」过于宽泛；可收敛为「首次接触的玩家能否理解主要操作」「目标能否辨认」「操作是否引发误触」等具体问题。指标需要适合当前玩家与阶段，不编造普适阈值。

原型只做到足以回答问题。功能可行不自动证明体验成立；一次正向反馈也不证明市场需求。

## 4. 里程碑：每一批任务必须共同交付一个结果

| 字段 | 内容 |
| --- | --- |
| 阶段目标 | 玩家将能体验什么，或团队将消除哪个关键未知 |
| 交付物 | 可运行版本、实验结论或代表性样板 |
| 完成条件 | 可观察的行为、质量或证据 |
| 输入与依赖 | 已确认规则、资源、工具或前一阶段结果 |
| 范围边界 | 本阶段保留、简化和延后的内容 |
| 阶段后决定 | 继续、修改、缩小范围或停止 |

常见阶段按项目风险裁剪：

1. 关键问题实验，确认方向或技术可行性。
2. 最小可玩版，内容少但完整一局能结束并重来。
3. 代表性样板，用目标质量验证美术、操作和制作流程；小项目可与首版合并。
4. 按已验证方法补齐内容，修复影响体验的问题，准备发行产物。

未来阶段先列目标和依赖；近期阶段才展开任务。通过实际制作速度更新成本估计。

样板选择能代表核心机制、目标表现、技术负载或制作难点的片段，不限定为游戏开头。开头过于简单时，它未必能代表后续制作成本。

## 5. 任务卡：从里程碑走到可执行工作

| 字段 | 要写到什么程度 |
| --- | --- |
| 编号与归属 | 指向阶段成果和方案中的规则，避免复制整份策划 |
| 目标 | 一句话描述可验证的结果 |
| 输入与依赖 | 上游任务、已确认参数、资源、接口；缺项明确标记 |
| 要做 / 不做 | 当前边界，避免顺手扩充功能 |
| 交付与集成 | 交付文件或资源，以及接入既有流程的位置 |
| 验收 | 初始条件 → 玩家操作或事件 → 预期结果，并覆盖关键失败路径 |
| 验证方式 | 自动检查、运行验证、目标设备体验分别由谁完成 |
| 回退点 | 可恢复的版本或受影响文件备份，标明本次改动边界 |
| 未知与降级 | 卡住时先调查什么，可怎样缩小范围；工作量估计附假设 |

可开工标准：输入足够、边界明确、依赖可用、结果能独立观察。若一项任务同时要解决多个未知、存在多个独立交付物，或无法说明怎样验收，继续拆小。

「一个结果」不等于只允许一条验收条件。条件可以覆盖正常路径、失败路径与必要回归；若条件对应多个互不依赖的结果，再拆为不同任务。

区分「调查任务」与「实现任务」：调查交付结论和证据，实现交付能集成的能力。代码函数清单属于任务内部步骤，通常不适合作为用户侧里程碑。

检查覆盖关系：当前交付范围中的每项需求对应哪个阶段，近期需求由哪张任务卡交付，验收证据记录在哪里。用简短列表即可查漏、发现额外工作；远期任务保持粗粒度，避免为填满表格提前编造实现细节。

### 一个任务示例：开镜保持当前观察中心

以下仅演示任务形状，不决定任何游戏采用此玩法、倍率、场景或技术栈。

- **归属**：验证观察操作的阶段。
- **目标**：玩家在当前朝向开镜，画面中心的参照物继续位于中心。
- **前置**：普通观察与拖动已可用；观察状态有统一来源；提供可辨认的测试参照物。
- **要做**：读取当前观察状态进入放大视野，支持放大后拖动，退出时保留新的朝向。
- **不做**：射击、命中反馈、装填、美术替换和额外关卡。
- **交付与集成**：开镜输入连接现有观察控制器，UI 从统一状态读取模式；提交可运行预览及验证记录。
- **验收**：拖动使参照物居中 → 开镜 → 参照物仍居中；镜内拖动 → 退出 → 朝向不回到开镜前；重复切换不积累偏移。
- **验证**：必要的状态与坐标检查由助手完成；授权范围内运行验证；目标设备的手感由用户或约定测试者确认。
- **回退**：记录开工前观察控制器与 UI 的可恢复版本；撤回本次开镜接线时保留已经通过的拖动观察能力。
- **未知处理**：如缩放与坐标换算方案未确定，先做小实验比较并记录结果，再接入正式控制器。

## 6. 避免任务做完却拼不起来

在相关任务开工前约定最小连接契约：共享状态由谁持有、输入输出是什么、坐标和资源标识如何统一、结束与重来如何清理。只写当前阶段真正需要的契约，避免预先搭建大型框架。

最小可玩版就应包含必要的集成。此后每个增量接入可运行基线，先验证协作再扩充依赖它的内容。后期整体集成检查用于发现跨流程问题，不作为第一次把系统接在一起的时间点。

将「把资源放进项目」与「在运行版本中正确使用资源」区分开。美术任务说明格式、尺寸、透明背景、命名及接入位置；程序任务说明输入、反馈和状态变化。按需要增加集成任务。

最小闭环建成后，每个可玩增量都回归：能开始吗、主要操作有正确结果吗、能结束并重来吗。关键路径断了就优先恢复，再继续依赖它的任务。

缺陷、体验问题和新需求分别记录：复现并修复缺陷；提出假设并验证体验问题；评估新需求的范围、依赖和成本。反馈要回写方案与任务状态，避免多个版本各自演化。

## 7. 完成与协作

任务完成证据包含：交付物、验收结果、已知限制、未验证项和下一项可开展工作。类型检查、构建、功能验证和真机体验分别记录。

需要阶段出口表、技术测量记录、范围变更记录或汇报格式时，使用 [交付检查点](delivery-checkpoints.md)。

用户主要提供体验目标、取舍和目标设备反馈；助手负责提出可比较方案、整理依赖、细化任务，以及获准后的实现与技术验证。审批与验收沿用当前用户约定，不把每个技术步骤都变成人工等待点。

方法参考：[Riot 原型实践](https://www.riotgames.com/en/r-and-d-office/prototype-building-a-games-substance)、[Riot 研发阶段](https://www.riotgames.com/en/r-and-d-office/engineering-in-riot-r-d)、[Roblox 原型指南](https://create.roblox.com/docs/production/game-design/prototyping)。本文件的模板是为小型游戏与人机协作整理的建议结构。
