# 交付检查点：出口、证据、范围与回退

按项目风险和当前协作约定裁剪。阶段检查用于决定后续依赖能否推进，不能用新增审批代替验证。

## 1. 阶段出口

| 阶段 | 进入后续工作的证据 |
| --- | --- |
| 定义范围 | 核心循环、当前范围、通过标准和主要未知已清楚；影响方向的决定已按约定确认，未知有验证安排 |
| 最小可玩版 | 内容极少但能开始、完成主要操作、结束和重来；关键技术风险通过约定验证，或调整方案后已移除相应依赖 |
| 代表性样板 | 一个有代表性的片段达到约定的体验与质量，制作流程及主要资源成本可重复；玩家能理解操作、反馈和结果 |
| 内容扩展 | 新增内容沿用已验证的制作方式；本次内容通过适当检查，既有关键路径未被破坏 |
| 发行准备 | 实际发行构建在目标设备上的完整路径已按约定验证，已知问题与待验证项透明；资料、资质和提交方式符合所选通道 |

某阶段没有过出口时，优先处理阻断它的工作；不把「代码写完」或「口头觉得可以」作为证据替代。用户要求逐任务或逐关验收时，按约定等待该验收；否则沿用阶段验收与既有执行授权。

根据玩家目标定义体验标准。「愿意再玩」是有用的观察线索，但连玩几局、用哪些设备和什么阈值，应在项目中约定，不作为所有游戏的统一证明。

样板需要代表目标质量。视觉是核心机制或主要风险时，在原型阶段就提供足够有代表性的美术；其余资源先按验证需要简化。

## 2. 早期技术验证

将可能影响选型或核心体验的技术问题提前做成小实验。复用最小可玩版记录轻量基线；按风险追加测量，不默认建立复杂性能工具或提前进行大规模优化。

网页或移动端项目可以从以下项目中选择：

- **启动与加载**：冷启动到首次可交互的时间、加载失败或白屏情况。
- **产物与网络**：首包或首屏必需资源大小、网络条件与缓存状态。明确传输大小与解压后大小的区别。
- **运行表现**：代表性操作下的帧率或卡顿、资源压力与兼容问题。
- **关键使用路径**：触控、音频、后台恢复、屏幕适配等当前项目实际依赖的能力。

测量记录包含：构建版本或标识、设备及浏览器或运行容器版本、网络与缓存条件、测量方法、结果、目标预算、结论与下一步。

预算由目标设备、产品体验和可用资源决定。未约定时提出带假设的候选预算；没有实测时标记未测，不填成通过。用户限制测试范围时，保留该限制并说明缺少的证据。

结果影响核心体验或技术路线时，先定位瓶颈，比较简化内容、调整资源、优化或重新选型的成本，再决定后续投入。记录原始报错、复现步骤和已尝试办法；重复尝试需要新的依据。

## 3. 范围基线与变更

每阶段保留三类清单：当前必须完成、允许简化、后续待办。具体数量、关卡与系统由项目目标决定，不把某份参考文档的 v1 清单复制成通用范围。

新想法先记录，评估：

1. 它是否是当前体验或阶段出口所必需的？
2. 引入哪些依赖、资源制作和新增验证？
3. 若进入当前阶段，替换哪些工作，成本和完成预期如何变化？

通常在阶段边界决定是否纳入；发现核心假设不成立、阻断缺陷或必须处理的外部变化时，及时调整。范围冻结用于减少随意扩张，不阻止有依据的修正。

同一玩法下的关卡优先用配置表达数量、位置、难度等变化。新增机制或表现需要代码时，按新工作评估；不承诺任何新关卡都只改数字。调难度时尽量控制变化，方便判断体验差异的原因。

SDK、账号和平台能力按实际需求安排。核心体验或技术可行性依赖某能力时，应提前验证；其余在本地循环成立后逐项接入。

## 4. 回退与任务状态

开工前确定与本次改动匹配的恢复点：可定位的 Git 版本、局部提交或受影响文件备份。已有未提交改动时先识别归属并保留，不为制造基线而把无关改动一起提交，也不使用破坏性恢复覆盖他人工作。

任务状态区分：待开展、进行中、受阻、待约定验收、已接受、需返工。技术验证通过可以作为证据记录；需要用户体验验收时，不能自动把它升级成已接受。

只承接当前任务所需的改动。发现必要前置调整时，说明与验收目标的关系，按授权处理或单独排任务；独立重构另行评估。

## 5. 试玩、回归与问题分级

在合适里程碑安排未参与制作的目标玩家体验，观察实际行为与卡点，减少提示性指导。记录原因假设，区分操作、规则理解、难度、反馈与运行问题，不能把卡住一律归因于缺少引导。

日常变更按影响范围检查相关能力和关键路径；阶段或发行构建验证完整流程。测试覆盖和环境数量随风险选择，避免每个微小改动都无差别重跑全部检查。

问题记录包含复现条件、影响、严重度、处理安排和验证证据。区分玩不下去的阻断、损坏核心体验的严重问题、一般瑕疵及新需求建议。影响已承诺交付标准的问题需要修复，或调整范围并获得接受；其他问题按影响排序，保留已知问题清单。

## 6. 汇报与交接

每个交付增量简洁报告：

- **交付**：玩家或项目现在增加了什么能力，涉及哪些主要文件或资源。
- **证据**：执行了哪些验证，实际结果如何，目标设备是否已测。
- **限制**：已知问题、未验证项，以及对后续工作的影响。
- **恢复点**：从哪里恢复本次改动，当前可玩基线是什么。
- **下一步**：当前依赖允许开展什么；需要约定验收时明确停在验收点。

用户负责产品取舍与最终体验判断；助手负责提出选择、说明代价并执行获准工作。编辑器中的建场景、导入、挂脚本或预览，可以根据可用 API、MCP、CLI、文件工具及人工操作的可靠性分配，无需固定为全部手动。

## 7. 最终交付清单

按约定范围核对：可运行构建或访问入口、版本和运行说明、当前方案与任务状态、维护所需的源码和资源配置、已知问题及未验证项。交接给其他人时，确认对方能够据此启动和验证产物。

设置、存档、退出与进度处理按项目需求决定，不能为满足通用清单而临时添加系统。交付声明写清完成的范围和证据；某个原型任务完成，不等于完整产品或发行工作已完成。
